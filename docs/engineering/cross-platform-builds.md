# Cross-platform development and builds

This is the working agreement for developing AsterLab on Linux and Windows
without pretending the two platforms produce the same artifacts.

## 1. Ownership

| Environment | Owns |
|---|---|
| Linux VPS | Rust Core, typed CLI, SDK/schema, module validators, Go non-GUI packages, fixture, Agent orchestration |
| Windows host | MyGo/Slint desktop app, MSVC `Runs.dll`, real-window UI, screenshots, installers, final GUI E2E |
| GitHub | source of truth, branches, PR review, CI status, acceptance records |

The source is shared. The native library, the app binary, and the visual
evidence are per-platform artifacts.

## 2. What Git tracks

Commit:

- Rust and Go source, including `src/cli.rs`, `crates/**`, and
  `prototypes/mygo-run/**`.
- Generated native bindings: `modules/runs/<module>_native.go` and
  `modules/runs/rust/src/mygo.rs`. Do not hand-edit them.
- `mygo-plugin.json`, including its per-platform published-build entries.
- `Cargo.lock`, `go.sum`, scripts, fixtures, and documentation.

Never commit:

- `target/`, `prototypes/mygo-run/target/`, `release/`, `dist/`, or
  `prototypes/mygo-run/.mygo/`.
- `Runs.dll` or `libRuns.so`; they are local build outputs.
- `labworkbench` / `labworkbench.exe` build outputs.
- Any `labworkbench.sqlite` data directory, fixture output, or screenshot
  generated by a test run.

`mygo-plugin.json` may contain both `windows-amd64` and `linux-amd64` entries.
They point at different published files; one does not replace the other.

## 3. Toolchains and pins

| Tool | Version / pin |
|---|---|
| Go | 1.27.3 |
| Rust | 1.99.0 stable |
| MyGo | `github.com/egoist/mygo@v0.8.4-0.20261108220316-c4197b7fe562` |
| Python | 3.12+ for `scripts/rc3-fixture.py` (3.14 measured on Windows) |
| Linux native deps | `build-essential`, `pkg-config`, `libssl-dev`, `libsqlite3-dev`, `fonts-droid-fallback` |
| Windows native deps | MSVC C++ build tools, Windows SDK, Rust MSVC toolchain |

Do not float the MyGo pin. A different MyGo can change generated bindings,
library naming, or `mygo-plugin.json` semantics.

## 4. Build matrix

| Artifact | Linux | Windows | Committed |
|---|---|---|---|
| Rust CLI | `cargo build --bin labworkbench` → `target/debug/labworkbench` | same → `target\debug\labworkbench.exe` | no |
| Core/App tests | `cargo test --manifest-path ...` | same | no |
| Native Runs | `mygo native build -target host ./modules/runs` → `.mygo/native/linux-amd64/libRuns.so` | `mygo native check .\modules\runs` → `.mygo\native\windows-amd64\Runs.dll` | `.so`/`.dll` no; manifest yes |
| Go tests | `scripts/mygo-native-linux.sh` | `mygo native check` then `go test ./...` | no |
| Desktop app | not supported without porting | `scripts/mygo-build.ps1` → `dist\mygo-run.exe` + `Runs.dll` | no |
| Acceptance fixture | `scripts/rc3-fixture.py` | same | script yes, data no |
| GUI E2E | not available | `scripts/gui-e2e-v11.ps1` | script/evidence policy applies |

The Go import path and generated Go binding are identical on both platforms.
`mygo` selects `Runs.dll` on Windows and `libRuns.so` on Linux. Never copy one
platform's native library over the other.

## 5. Linux loop

```bash
cd AsterLab
export CARGO_TARGET_DIR=/srv/asterlab-build/target
export CARGO_BUILD_JOBS=2
export CARGO_INCREMENTAL=0

cargo test --bin labworkbench
cargo test --manifest-path crates/asterlab-core/Cargo.toml
cargo test --manifest-path crates/asterlab-app/Cargo.toml
cargo build --bin labworkbench

# Builds .mygo/native/linux-amd64/libRuns.so, then runs all Go tests.
scripts/mygo-native-linux.sh

# Fixture: data must be a fresh temp directory (or under target/CARGO_TARGET_DIR).
RC3_DATA="$(mktemp -d)"
LABWORKBENCH_CLI="${CARGO_TARGET_DIR}/debug/labworkbench" \
ASTERLAB_DATA_DIR="$RC3_DATA" \
python3 scripts/rc3-fixture.py
```

The fixture writes IDs to `$RC3_DATA/rc3-ids.json`. A non-empty directory is
refused unless it contains the `.rc3-fixture` marker from a previous run.
`workflow.inspect_tree` is now computed by Rust Core on Linux; it no longer
requires `ASTERLAB_APP_BIN`. The GUI Canvas/Run rail still uses the Go engine,
so both producers stay checked against the shared RNA evidence.

Linux Go tests currently write headless PNG evidence into tracked paths. Do not
commit those changes; discard PNG churn after a run or use a disposable
worktree for clean CI. Windows remains the authority for visual evidence.

## 6. Windows loop

```powershell
cd AsterLab
cargo test --bin labworkbench
cargo test --manifest-path crates\asterlab-core\Cargo.toml
cargo test --manifest-path crates\asterlab-app\Cargo.toml
cargo build --bin labworkbench

cd prototypes\mygo-run
go run github.com/egoist/mygo/cmd/mygo@v0.8.4-0.20261108220316-c4197b7fe562 native check .\modules\runs
go test ./...
cd ..\..

.\scripts\mygo-build.ps1
```

`mygo-build.ps1` creates `prototypes\mygo-run\dist\mygo-run.exe`, copies the
matching `Runs.dll`, and writes a `BUILD_INFO.txt`. The final GUI gate uses
`scripts/gui-e2e-v11.ps1` with its required database, app, CLI, and Run
arguments.

## 7. Change impact

| Change | Linux check | Windows check |
|---|---|---|
| `crates/asterlab-core` / `asterlab-app` | Cargo tests; rebuild CLI | Cargo tests; rebuild CLI; native check; app build |
| `src/cli.rs` | Cargo tests; native module build | Cargo tests; native check; app build |
| `modules/runs/runs.go` (interface) | regenerate/check native binding; build `.so`; Go tests | regenerate/check; build `.dll`; Go tests; app build |
| `modules/runs/rust/src/lib.rs` | native check; Go tests | native check; Go tests; app build |
| `prototypes/mygo-run/internal/**` | Go tests | Go tests; GUI E2E if UI-facing |
| `prototypes/mygo-run/main.go` or GUI code | not buildable as the desktop app | app build; GUI E2E |
| `scripts/rc3-fixture.py` | fixture + guard cases | fixture with `LABWORKBENCH_CLI`/`.exe` |

`src/cli.rs` is included by both the CLI and the native Runs module. A change
there is not validated by a CLI-only test run.

## 8. Merge gates

Linux/VPS gate:

1. Rust CLI, Core, and App tests pass.
2. Host-native `libRuns.so` is built.
3. `go test ./...` passes.
4. Fixture produces `assess: warning []` and three protocol tasks.
5. No `target/`, `.mygo/`, SQLite, or PNG test churn is included.

Windows gate:

1. Rust tests and `mygo native check` pass.
2. `go test ./...` passes with the host `Runs.dll`.
3. `mygo-build.ps1` produces the app and matching DLL.
4. The requested GUI E2E/acceptance case passes on the merged baseline.
5. Screenshots and installer evidence are attached to the acceptance record.

A PR is not “cross-platform verified” until both gates relevant to its change
have run. A Linux-only green run does not prove the GUI.

## 9. Platform boundaries to keep

- SQLite data is local to one platform and one `LABWORKBENCH_DATA_DIR`; never
  share a data directory between Windows and Linux.
- `CARGO_TARGET_DIR`, `GOTMPDIR`, and `GOCACHE` are per-host; do not point two
  platforms at one directory.
- Prefer LF for source and generated Go/Rust/JSON. Keep PowerShell scripts
  CRLF. If line-ending churn appears, fix `.gitattributes`; do not renormalize
  the whole tree as part of a feature PR.
- Do not run `cargo fmt` wholesale; the tree is not clean and the diff would
  bury review. Format touched code only.
- `workflow.inspect_tree` now has a Rust Core producer for the CLI. The GUI
  Canvas/Run rail still uses the Go producer; keep the shared evidence test
  green and migrate the GUI producer before calling the two implementations a
  single code path.
