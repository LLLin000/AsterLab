# Kandev official automation: capabilities and limits

Evidence below is from Kandev’s official documentation (not third-party descriptions). “Documented” means the source explicitly says so; unknowns are not guarantees.

## Workflow states and transitions

- **Documented:** A workflow is an ordered set of steps; step is task process position, distinct from runtime/session state. Moving a task changes its step and does not prove the agent ran, code was committed, review passed, or a PR merged. Entry actions can set plan mode, reset context, or auto-start; turn-start/turn-complete events can move tasks; turn-complete/step-exit can disable plan mode. Approval/review steps and steps without auto-start are human gates. ([Tasks and Workflows — Understand the model](https://kandev.ai/docs/tasks-and-workflows#understand-the-model); [Automation and MCP — Workflow events and human gates](https://kandev.ai/docs/automation-and-mcp#workflow-events-and-human-gates))
- **Documented:** Auto-start is subject to routing, authorization, WIP, session state, dependencies, and active-session rules; a move waits for a running agent. Inspect source and destination events because paired moves/starts can loop. ([Tasks and Workflows — Move a task with one-time entry options](https://kandev.ai/docs/tasks-and-workflows#move-a-task-with-one-time-entry-options); [Automation and MCP — Workflow events and human gates](https://kandev.ai/docs/automation-and-mcp#workflow-events-and-human-gates))
- **Documented:** A blocked dependency prevents automated starts/promotions; manually starting is an explicit override. Successful predecessor completion resolves a dependency; Failed/Cancelled does not and Kandev does not automatically retry the predecessor. ([Tasks and Workflows — What blocked means / When a predecessor does not succeed](https://kandev.ai/docs/tasks-and-workflows#what-blocked-means))
- **Unknown:** The docs do not promise that a workflow-step change performs Git operations, merges a PR, or is equivalent to runtime completion.

## Task/session lifecycle, resume, cancellation

- **Documented:** Tasks can be created with or without starting an agent; sessions are conversations attached to tasks, and multiple sessions may share the task environment. Session actions include Stop (cancels active turn), Restart (stop then resume same session, preserving history/workspace), Resume (attempts to continue completed/failed/cancelled session), and Delete (removes conversation, not task files). ([Tasks and Workflows — Understand the model / Create a task](https://kandev.ai/docs/tasks-and-workflows#understand-the-model); [Sessions and Review — Manage session state](https://kandev.ai/docs/sessions-and-review#manage-session-state))
- **Documented:** A task automation run is a traceable thread with task/session/turn identities. New-task-per-run creates separate sessions/environments; continuation reuses one task, primary session, conversation, and worktree, without resetting or rebasing checkout. A finished run parks in `WAITING_FOR_INPUT`, not `COMPLETED`. ([Automation and MCP — What a firing produces](https://kandev.ai/docs/automation-and-mcp#what-a-firing-produces))
- **Documented:** A run cannot wait for permission response; Kandev rejects the request and marks the run failed. Choose a profile whose constrained actions do not require an interactive permission prompt. ([Automation and MCP — What a firing produces](https://kandev.ai/docs/automation-and-mcp#what-a-firing-produces))
- **Unknown:** Resume depends on the executor’s saved session/runtime records; docs explicitly warn missing worktree, expired remote environment, removed profile, or missing runtime record may require a fresh session. No universal resume guarantee. ([Sessions and Review — Manage session state](https://kandev.ai/docs/sessions-and-review#manage-session-state))

## Triggers, concurrency, WIP and backpressure

- **Documented:** Workspace automations create work from schedules, GitHub PRs, webhooks, or manual trigger. Scheduled mode and webhook mode are mutually exclusive in the editor; scheduled plus GitHub condition are independent triggers, so a GitHub condition does not constrain scheduled runs. ([Automation and MCP — Automation and MCP / Trigger behavior](https://kandev.ai/docs/automation-and-mcp); [Trigger behavior](https://kandev.ai/docs/automation-and-mcp#trigger-behavior))
- **Documented:** Scheduler checks every 30 seconds; missed schedule during backend downtime fires once on the next check, not once per missed occurrence. GitHub PR evaluator polls open PRs every 60 seconds, needs a repo list and Opened event, evaluates currently open matches on first pass, and deduplicates per automation/repository/PR. ([Automation and MCP — Schedule / GitHub pull requests](https://kandev.ai/docs/automation-and-mcp#schedule))
- **Documented:** Automation default concurrency is one; increasing it is intended only where parallel work is safe. Reused sessions always have one active run. Workflow WIP queueing delays launch until capacity becomes available; dependencies do not bypass WIP. ([Automation and MCP — Create a workspace automation](https://kandev.ai/docs/automation-and-mcp#create-a-workspace-automation); [Tasks and Workflows — Chains that run themselves](https://kandev.ai/docs/tasks-and-workflows#chains-that-run-themselves))
- **Unknown:** Docs describe admission and queues but do not promise a global execution limit, fairness/order across all sources, or a universal backpressure policy for every trigger type.

## GitHub PRs, checks, approvals

- **Documented:** GitHub integration supports PRs, issues, reviews, checks, repository discovery, task association, and provider-triggered work. Push and CI-check automation triggers require a workspace GitHub App connection subscribed to `push` and `check_run`; webhook delivery is HMAC-verified. Push ignores branch deletion; CI checks can filter conclusion/name/head branch and dedupe by check-run ID. ([Integrations — GitHub](https://kandev.ai/docs/integrations#github); [Automation and MCP — GitHub push and CI checks](https://kandev.ai/docs/automation-and-mcp#github-push-and-ci-checks))
- **Documented:** “Pull request merged” automation watches PRs linked to tasks in its workspace; polling can take up to a minute. No creation-time backfill; first qualifying update event triggers. Concurrency-cap skip or failure before task creation does not consume its dedup key, but there is no durable retry queue; another PR update is needed. ([Automation and MCP — GitHub pull requests merged](https://kandev.ai/docs/automation-and-mcp#github-pull-requests-merged))
- **Documented:** Human review remains a workflow gate; PR step draft/review status uses that step’s automation. GitHub App and personal identities differ: App acts as the automation identity; user-triggered review/merge uses personal identity first, then human automation identity, then App. ([Tasks and Workflows — Quick path](https://kandev.ai/docs/tasks-and-workflows#quick-path); [Integrations — Automation and personal identity](https://kandev.ai/docs/integrations#automation-and-personal-identity))
- **Unknown:** No blanket claim that Kandev automatically approves or merges every PR; permissions, workflow configuration, provider status, and human gates still matter.

## Errors, retries, webhooks, API and security

- **Documented:** Task automation retries can be disabled, finite, or unlimited, with fixed/exponential delay. If provider acceptance cannot be established, run remains pending and is not resent automatically; capacity is held until exact turn completes or observed execution is confirmed stopped. ([Automation and MCP — Automatic retries](https://kandev.ai/docs/automation-and-mcp#automatic-retries))
- **Documented:** Webhook endpoint is `POST /api/v1/automations/webhook/{automationId}` with `X-Webhook-Secret` and required `X-Kandev-Delivery-ID`; IDs deduplicate per automation. Bodies are limited to 1 MiB; invalid JSON/projections return 400, oversized bodies 413. Optional filters run before dedupe/capacity; rejected deliveries return uniform 200 and are recorded skipped. Use TLS; secret is visible to users with Kandev settings access and is stored with automation rather than encrypted provider-secret storage. ([Automation and MCP — Webhook delivery contract / Webhook](https://kandev.ai/docs/automation-and-mcp#webhook-delivery-contract))
- **Documented:** External MCP actions are validated against the live mode-specific `tools/list` schema; invalid/missing/unknown top-level fields return tool errors before handler action. External MCP tool access is subject to client authorization. Credentials delivered through MCP or executor profiles are available to the receiving agent. ([Automation and MCP — opening overview / Task creation boundaries](https://kandev.ai/docs/automation-and-mcp); [Quick path](https://kandev.ai/docs/automation-and-mcp#quick-path))
- **Documented:** GitHub integration credential and task Git credentials are separate. App-backed managed task credentials are repository/task-scoped leases; PAT/CLI bearer tokens, if delivered to trusted subprocesses, retain provider-granted scopes. Provider secrets are encrypted at rest, but backend decrypts them to call APIs. ([Integrations — opening overview / Authenticate](https://kandev.ai/docs/integrations); [Choose task Git credentials](https://kandev.ai/docs/integrations#choose-task-git-credentials))
- **Unknown:** The docs do not provide a general public API permission matrix or guarantee exactly-once effects for retries/recovery. Webhook deduplication prevents duplicate firing by key/ID, but callers should make downstream actions idempotent. ([Automation and MCP — Webhook](https://kandev.ai/docs/automation-and-mcp#webhook); [Sessions and Review — Interruption continuation](https://kandev.ai/docs/sessions-and-review#interruption-continuation))
