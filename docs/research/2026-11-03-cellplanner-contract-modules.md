# 实验设计契约与可复用步骤块：调研与产品方案（2026-11-03）

状态：产品与数据契约建议，尚未接入当前原型运行时。本文用于验证模块边界与 Agent 合同，不代表已有 CLI 命令或功能。

术语以项目根目录 [`CONTEXT.md`](../../CONTEXT.md) 为准。本文前半的 `module.*` 是未纳入 V1 的早期字段扩展提案；后文早期写作的“Protocol 片段/操作模块”均统一称“步骤块 `ProtocolBlock`”。

## 结论

采用“固定科学核心 + 类型化自定义字段 + 可版本化 Protocol 步骤块”的组合，不把整个设计对象改成随意键值表，也不为每类实验建立独立工作流。

固定核心表达实验单位、处理组、样本来源/分配、检测目标、Protocol 引用、Run 和来源证据。罕见设计细节可用类型化自定义字段补充；程序步骤的复用统一交给步骤块。这样可扩展实验表达，同时不把科学关系降成无约束 JSON。

**当前收敛决定：** V1 的主体是固定科学核心 + 可复用步骤块 + 确定性计算工具。本文前半段的 Assay 设计字段模块注册表和 module.* 命令是早期候选，不纳入 V1 主路径；只保留类型化自定义字段作为长尾信息出口。

## 调研到的成熟做法

- ISA 模型把材料、Protocol 过程和数据结果明确关联；Assay 记录测量类型、技术和应用的 Protocol，也允许材料分样或合并。这说明实验核心应表达“材料经过什么步骤产生什么测量”，而不是把关键关系放入随意扩展的文本字段。[ISA Abstract Model](https://isa-specs.readthedocs.io/en/latest/isamodel.html)
- Benchling 的 Registry schema / Fieldset 允许多个实体复用一致的字段约束，同时保留各实体独有字段；字段有固定类型和 required 约束。这是“共享契约 + 局部定制”的好参照。[Benchling: Configure Registry schemas](https://help.benchling.com/hc/en-us/articles/39935326052493-Configure-Registry-schemas)
- eLabFTW 支持把有类型的自定义字段组织成组，并放进模板，让新实验带着既定结构开始；其文档也说明字段值存在 JSON metadata 中。CellPlanner 可以借鉴字段组与模板体验。Agent 写入保持严格的工具外层契约，同时允许用类型化自定义字段表达研究者的领域差异；不把 JSON metadata 编辑口当作默认输入方式。[eLabFTW: Custom fields](https://doc.elabftw.net/docs/usage/user-guide/custom-fields/) [eLabFTW: Import / Export](https://doc.elabftw.net/docs/usage/import-export/)
- JSON Schema 可通过封闭对象拒绝未声明字段；但动态模块的字段在全局设计 schema 编译时未知，需要“通用外层输入校验 + 精确模块版本校验”两段校验。不要把模块版本用不谨慎的 allOf 拼接：additionalProperties 在组合 schema 中有容易误判的边界。[JSON Schema: Objects and additionalProperties](https://json-schema.org/understanding-json-schema/reference/object)

## 早期探索：可复用的设计字段组（不作为 V1 主机制）

### 1. 固定核心不交给模块改写

固定核心继续覆盖：

- 研究问题、分组和实际处理条件
- 实验单位、独立 n 与技术重复的区别
- Assay、Endpoint、时间锚点、样本分配及来源
- 计划载体 / 孔板、Protocol 精确版本、执行 Run
- 来源证据、未决冲突、版本和执行偏差

模块不得重新定义或覆盖这些字段。例如，自定义字段不能把 6 个孔声明成 6 个独立样本，也不能替换样本来源关系。

### 2. 模块定义是可复用、不可原地变更的字段契约

模块定义包含：

- 稳定的 module_id、名称、用途、适用范围和版本号
- 有稳定 key 的字段列表；label 可按实验室习惯命名，key 不随意更改
- 字段类型、单位、范围 / 枚举选项、是否可重复成行
- required_on：保存草案时是否必填，或仅在创建 Run 时必填
- 可选的 semantic_role，只能从产品内置白名单选择

建议第一版仅支持 assay 级模块。字段类型限定为 text、long_text、integer、decimal、boolean、enum、multi_enum、quantity、group_ref、assay_ref、protocol_version_ref、evidence_ref。引用字段必须指向现有核心记录，不能用自由文本伪装外键。

semantic_role 只用于调用已实现的确定性能力，例如 metadata、control_role、physical_slot_count、protocol_parameter。字段不必声明 semantic_role；没有内置语义的研究者自定义字段仍可保存、搜索、显示和导出，但不触发自动计算。未知 semantic_role 不能冒充已有引擎能力。不支持用户写公式、JavaScript、条件脚本或 SQL。

模块修订创建新版本；旧实验设计和 Run 继续指向旧版本。更改字段类型、含义或单位不能追溯改变已保存数据。

### 3. 设计实例引用确切模块版本

实例应保存 module_id、module_version_id、作用对象（V1 为 assay）和行数据。每行值按 module.get 返回的字段契约校验。概念示例：

    {
      "module_id": "assay.control-layout",
      "module_version_id": "module-version-17",
      "scope": {"type": "assay", "id": "cck8"},
      "rows": [
        {
          "row_id": "blank-1",
          "values": {
            "role": "reagent_blank",
            "group_ref": "group-no-cell-blank",
            "slot_count": 6,
            "evidence_ref": "evidence-0921"
          }
        }
      ]
    }

这不是当前 design.create 已接受的字段。它说明建议的数据形状：module 只能通过稳定 ID 绑定，且所有引用和值都由指定版本契约解释。

## 设计字段组 CLI 草案（非 V1 候选；不是 Protocol 步骤库）

本节 `module.*` 指的是给实验设计补充类型化字段组的早期想法，不表示铺板、染色或配液等操作步骤。它不属于当前 V1 的必做能力；若真实案例证明自由字段不够，再单独评估。可复用的实验操作统一由后文的 ProtocolBlock 读写与组合能力承载，避免 Agent 混淆两套“模块”。

建议按以下边界扩展，而不是增加一个无约束 generic set：

| 命令 | 输入 | 输出 / 副作用 |
|---|---|---|
| module.list | project_id、可选 scope | 列出模块 ID、当前版本、适用位置；只读 |
| module.get | module_version_id | 返回完整字段契约、类型、选项、单位、必填时机；只读 |
| module.validate | module_version_id、scope、rows | 返回逐字段路径的错误、待确认项、标准化值和可计算结果；只读，不写入 |
| module.create | 项目、名称、scope、受限字段定义 | 创建 v1；写入 |
| module.revise | module_id、expected_version、字段变更 | 追加不可变新版本；写入 |
| design.create / design.revise | 核心设计 + 模块实例 + expected_revision | 严格校验工具外层、字段类型及版本冲突；领域问题随草案保存为 issues，执行或冻结操作再按其明确要求检查阻断项 |

模块动态校验错误必须给稳定 code 和字段路径，例如 MODULE_FIELD_UNKNOWN、MODULE_VALUE_TYPE_MISMATCH、MODULE_REFERENCE_NOT_FOUND，并告诉 Agent 应读取哪个模块版本或修正哪一行。设计写入仍需 expected_revision；更新模块定义不能悄悄改写旧设计。

动态 schema 不是任意键值输入：CLI 工具 schema 严格约束外层结构，module.get 提供指定版本的字段合同，module.validate 和写入端按该合同校验。外层拼写错误、字段类型不匹配、无效单位等结构问题应拒绝；如果研究者需要新字段，可通过 module.create / revise 增加类型化字段，而不需要修改程序代码。科学设计上的缺项、未决引用、建议性规则冲突应作为有路径的 issue 保存到草案，不应一概拒绝写入；只有执行某个明确操作必需的条件才成为该操作的 blocker。

## UI 的呈现方式

- 用户在检测卡里按需选择“添加设计模块”，不新开 Agent 页面。
- 模块标题使用用户语言，如“对照与附加孔位”“成像参数”“样本处理条件”；内部 module_id / semantic_role 不暴露给日常填写者。
- 模块默认折叠，只显示已填行数与关键摘要；打开后按表格编辑，可新增、复制、删除行。
- 保存草案允许未知值为空；创建 Run 时才根据 required_on=run 的字段给阻断，并指出字段、原因和影响。
- Agent 使用同一 CLI 读写同一设计对象。高影响改动先做字段 diff 与计算预览，用户确认后再提交；不另造“Agent 草稿”数据模型。
- 自定义模块作者面板只给少量安全字段类型和枚举编辑，系统自动生成表单与验证，不让作者编程。

## 用既有实验检验模块边界

### L929：CCK-8 对照

可以用一个 assay 级模块记录“试剂空白”行、它引用的既有无细胞空白组、每组需要的物理孔数和来源证据。这样孔位需求不再塞在 controls 文本里，同时不会把空白孔误当独立 n。若来源没有明确孔数，留空并返回“未计算”，不猜值。

### 生物膜：CV / CFU 控制与共板

可以为各 Assay 使用同一份控制字段契约，表示培养基空白、材料本底、隔离孔等类别。要把 54 个样品孔和 24 个隔离孔确认为同一块 96 孔板的 78 孔，还需要核心模型明确两项 Assay 共用同一 container pool；单独增加一个模块字段无法安全推断“共板”。因此 container pool 属于核心对象，不能靠自定义备注代替。若 54/24 或共板关系未确认，系统只显示已知数和待确认项。

### SA 铜梯度：样本来源

模块可增加特定记录用的、可搜索的定量字段，但不能用自定义字段解决 CFU / RNA 来自培养物还是 aliquot 的谱系问题。培养物、分样、合并和检测输入之间的关系是样本来源核心模型的 gap，应由正式的 Sample / Material 关系支持。

这三例说明：模块应承载检测特有、可配置的输入；跨实验都必须可靠计算的关系仍需固定建模。否则定制越多，Agent 越容易将关键事实藏进模块，计算和汇总就越不可靠。

## 验收标准

1. 模块字段只接受定义中的类型、范围、单位、枚举和引用；额外字段被拒绝，并指出精确路径。
2. 草案允许缺少执行时才必填的字段；Run 校验能给出阻断及影响说明，不自动补值。
3. 模块 v1 被设计引用后，修订只能产生 v2；旧设计、旧 Run 的快照始终可还原。
4. 同一模板可以用于不同 assay，字段实例不会因标签相似而自动互换。
5. L929 对照孔位在证据不足时不计算；生物膜共板只有 container pool 被明确配置后才聚合；SA 样本来源不接受任意文字替代核心来源 ID。
6. 用户能在同一设计页完成查看、填写和修改；Agent 只能通过已声明 CLI 操作相同字段，输入输出均有 schema。

## 建议的试做范围

最终收敛后，V1 暂不实现完整的 Assay module registry。必要的控制、样本分配、载体共池等科学关系先进入核心模型；少量长尾信息可用类型化自定义字段记录。先以 L929、生物膜和 SA 案例验证这些字段是否真有重复结构，再决定是否需要可复用的设计字段组。程序步骤复用统一走步骤块库。

## 附录：最小字段契约样例

下面是建议模块定义的形状，不是当前已支持的 CLI 输入：

    {
      "module_key": "assay.control-layout",
      "title": "对照与附加孔位",
      "scope": "assay",
      "repeatable": true,
      "fields": [
        {
          "key": "role",
          "label": "用途",
          "type": "enum",
          "required_on": "run",
          "semantic_role": "control_role",
          "options": [
            {"value": "reagent_blank", "label": "试剂空白"},
            {"value": "material_background", "label": "材料本底"},
            {"value": "positive_control", "label": "阳性对照"},
            {"value": "isolation", "label": "隔离孔"}
          ]
        },
        {
          "key": "group_ref",
          "label": "适用组别",
          "type": "group_ref",
          "required_on": "run",
          "semantic_role": "group_reference"
        },
        {
          "key": "slot_count",
          "label": "所需孔位数",
          "type": "integer",
          "required_on": "run",
          "min": 1,
          "max": 10000,
          "unit": "well",
          "semantic_role": "physical_slot_count"
        },
        {
          "key": "evidence_ref",
          "label": "来源记录",
          "type": "evidence_ref",
          "required_on": "draft",
          "semantic_role": "source_reference"
        }
      ]
    }

字段 key 是 Agent 和历史版本使用的稳定标识；label 可由实验室修改。enum 的 value 稳定，不能把显示文字当 ID。`group_ref`、`evidence_ref`必须解析为当前设计里的有效对象。`physical_slot_count`只表示容器需求，不参与独立 n。若要跨 Assay 汇总同一块板，还必须存在一个正式的共享容器池核心关系。

建议工具回执形状：

    {
      "valid": false,
      "issues": [
        {
          "path": "rows[0].values.group_ref",
          "code": "MODULE_REFERENCE_NOT_FOUND",
          "severity": "error",
          "message": "适用组别未引用当前设计中的组别。",
          "next_action": "调用 design.get 后从现有组别中选择。"
        }
      ],
      "derived": {"physical_slot_count": null}
    }

issues 的 path、code、severity、next_action 由确定性校验器产生；LLM 不负责判定值是否满足契约。模块作者填写描述和选项，不编写校验脚本。若新字段暂时没有计算规则，可以先作为普通类型化字段保存；只有用户要求系统自动计算某种新语义时，才需要增加对应的产品能力。

## 调研解释范围

Benchling / eLabFTW 文档证明的是产品如何组织结构化字段、复用 schema / template，并不证明某种自定义字段自动具有实验科学含义。ISA 的关系模型可作为样本与步骤互操作参考，也不能替代领域方法学判断。本文推荐将这些 UI / schema 模式与本项目的固定科学核心组合；具体模块的科学适用性仍要由 Protocol、记录证据或研究者确认。

## 步骤块、Protocol 与实验设计模板的组合

需要区分三种复用用途，但只实现一套模块契约和一套确定性校验，不建立三套独立引擎：

| 层 | 负责表达 | 例子 |
|---|---|---|
| 步骤块 `ProtocolBlock` | 一个可复用的小步骤或一组连续小步骤，具有输入、输出、参数和来源 | 配制 0.5% GelMA、铺板 / 接种、加样、染色 / 洗涤、成像 / 读板 |
| 操作方案 `Protocol` | 按顺序组合确切版本的步骤块，并绑定本次参数 | 一份 CCK-8 方法：接种 → 处理 → 加检测试剂 → 孵育 → 读板 |
| 实验设计模板 | 组合科学设计骨架、一个或多个 Assay、各自 Protocol 和适用模块 | 细胞处理 + CCK-8；可再组合活死染色 Assay 及其 Protocol |

设计模板实例化后生成普通实验设计草案。草案里的分组、实验单位、n、处理条件、比较目标、时间点、样本分配和计划载体都由研究者提供、由有来源的记录导入，或清晰标为待确认；模板不会因为复用而把这些参数伪装成科学事实。Run 再固定设计版本及其各 Assay 根步骤块和全部子块版本，实际日期、操作者、实际孔位、偏差及观察值属于 Run。

### 步骤块应有什么契约

步骤块按“有稳定输入/输出，且多个 Protocol 会重复使用”来划分，而不是按每一个动作拆分。例如：

- 铺板 / 接种步骤块：材料来源、容器类型、计划密度 / 数量、体积、操作后进入哪个步骤。
- 加样 / 处理步骤块：目标样本或孔位、加入的材料、单位化体积或浓度、适用组别、起始事件。
- 染色步骤块：样本输入、试剂与 Protocol 参数、孵育/洗涤步骤、产生的测量前样本。
- 成像 / 读板步骤块：测量对象、仪器设置、输出的测量指标 / 数据类型。

每个字段带稳定 key、类型、单位或选项、来源要求和必填时机；步骤输入/输出使用稳定样本、容器、Assay 或 Protocol 参数引用。是否允许顺序复用、分样、混样仍由样本关系和兼容性校验决定，不能仅由模块名称推断。用户可以在自定义 Protocol 中保留独特步骤；关键材料和参数仍应结构化，避免只在长文本中可见。

### 参数必须有明确“归属”

同一个数字可能属于不同对象，不能复制到多个表单：

- **Protocol 固定参数**：由具体方法版本确定，例如仪器读数设置或步骤顺序；变更时产生新 Protocol 版本。
- **设计参数**：研究者为本研究确定，可能按组变化，例如处理剂量或处理时长；进入分组 / Assay 计划。
- **Run 实际值**：执行时才知道，例如实际日期、操作者、实际加入量或偏差；进入执行记录。

Protocol 定义“这个步骤需要什么参数、类型/单位是什么、由哪一层提供”；设计模板把 Protocol 的参数绑定到核心设计字段或要求用户补填。执行前，系统按参数来源检查缺项，并指出“缺哪个值、影响哪个步骤”。ISA-Tab 将 Protocol 引用与参数值放在对应过程节点上，支持这类分层；Benchling 的 sub-template 让可复用内容插入多个条目 / 模板，并注明更新不会追溯改写已插入条目，适合借鉴组合和版本边界。[ISA-Tab Protocol 与 Parameter Value](https://isa-specs.readthedocs.io/en/latest/isatab.html) [Benchling Notebook templates 与 sub-templates](https://help.benchling.com/hc/en-us/articles/39939099777933-Configure-Notebook-templates-and-Template-Collections) [Benchling 插入 sub-template](https://help.benchling.com/hc/en-us/articles/39971013709965-Plan-experiments-and-collect-data-in-the-Notebook)

### “Protocol 成为模板”的产品交互

用户可以从两条入口进入同一条流程：

1. **从实验设计模板开始**：选择类似“细胞处理 + CCK-8”的模板。系统创建设计骨架、Assay 卡、已关联的 Protocol 版本和参数检查；研究者填写自己的分组、样本数、处理值和未知项。
2. **从 Protocol 开始**：选择一份 Protocol 后，系统显示“包含哪些操作步骤、需要哪些参数、可用于哪类检测”，然后生成一个待补设计草案；研究者再指定研究问题、比较组、实验单位、n 和分配。Protocol 本身不能自动决定这些科学设计。
3. **保存为新的实验设计模板**：从已校对的设计草案保存一份可复用组合，包含核心设计骨架、Assay 列表、各项 Protocol 精确版本、模块版本及参数绑定；明确区分固定方法参数、可编辑的默认值与待用户填写的参数。

一个设计可包含多项 Assay，每项 Assay 引用自己的 Protocol；所以“实验设计模板”是组合层，单一 Protocol 不需要承载整个多检测实验。模板修改创建新版本，既有草案和 Run 保持原版本；用户升级到新版时先看差异及受影响的步骤、参数、样本量和布局。

Agent 在此结构下应使用同一设计对象：读取模板 / Protocol 契约 → 预览实例化结果与缺项 → 按字段路径提出修改 → 验证计算与冲突 → 用户确认后创建草案或修订。可以提供 template.list / get / preview / instantiate 等明确定义工具；preview 只读，instantiate 创建可修订草案，所有输入输出遵循固定 schema。日常 UI 不出现“模块编排器”，只展示一个已命名模板和必要参数；高级用户才展开步骤构成。

### 应避免的边界错误

- 不把“做了铺板”当作生物学重复数，也不把“每孔操作一次”自动解释成实验单位。
- 不把 Protocol 里的固定值当成对照组、剂量组或研究比较。
- 不让一个 Protocol 覆盖多个独立 Assay 的来源、时间、终点和样本使用差异。
- 不允许改模板或模块后静默更新既有设计 / Run。
- 不自动把任何相似名字的 Protocol 步骤串在一起；通过稳定的模块 ID、参数绑定和版本引用组合。
- 不为表面复用而强行把每个独特步骤模块化。若一个步骤不需要结构化校验或跨 Protocol 复用，可保留 Protocol 正文，但仍标明它使用的材料和产生的样本 / 数据关系。

### 最小验证用例

1. 用“铺板 → 处理 → CCK-8 → 读板”的模块组合实例化一个设计草案；不自动填充未知的处理条件、n、时间或剂量。
2. 一项设计同时引用 CCK-8 与活死染色两个 Protocol；每项保留自己的时间锚点、样本使用政策与容器安排。
3. Protocol v2 修改某一步参数后，旧设计与 Run 仍显示 v1；用户从 v2 更新模板时看到受影响参数和计算的差异。
4. 将 Protocol 起草为设计时，系统仅创建待确认的研究设计骨架；没有依据时不生成主要比较、独立 n 或额外对照。

## 收敛原则：一个模块契约，不造通用流程引擎

上面的对象代表不同用途，不意味着要做三套编辑器、三套校验器或一个可编程工作流平台。为控制复杂度，建议收敛为：

1. **一套步骤块目录**：步骤块库是唯一的可复用程序步骤目录：每个块有版本化的输入、输出、类型化参数和来源；粒度可以是一条小步骤，也可以是连续步骤组合。未预见的新操作可以先创建自定义步骤块，无需新增代码或专用类型。
2. **Protocol 默认是步骤块清单**：每项引用某个步骤块的精确版本并绑定本次参数；需要临时补充时也可保存自定义步骤块。步骤块本身可由一条动作或一组连续动作组成；V1 不建设通用脚本或拖拽式流程引擎。暂不支持的分支 / 循环仍可作为自定义步骤块记录，并标注暂不能自动排程。
3. **实验设计模板是已有设计对象的可复用预设**：保存核心设计骨架、Assay 列表、精确的 Protocol 版本和步骤块参数绑定；不再额外引入 Workflow / Package / Study 实体。

因此底层仍是既定的“项目 → 实验设计版本 → Run”，样本分配、Assay、Protocol 引用作为设计内容；只有真正执行时才记录真实样本与实际值。步骤块、Protocol、设计模板是内容的复用与组合方式，不是新的导航层级。前台只给“从模板开始”和“从 Protocol 开始”两个入口，步骤默认按步骤块折叠显示。任何具体小步骤都可以保存为步骤块；UI 不要求每个动作单独占一行或让用户先理解“模块”概念。

### Agent 起草 Protocol：先保证能照做，再追求文字完整

Protocol 的主呈现应是短而具体的步骤表，不接受长篇自由文本作为唯一方法定义。每一步引用精确版本的步骤块；界面优先显示步骤块名称和本次参数，按需展开操作内容、参数来源与说明。

| 步骤信息 | 要能回答的问题 | 例子（仅示意格式） |
|---|---|---|
| 动作与对象 | 对什么材料做什么 | 向每孔加入检测试剂 |
| 参数与单位 | 加多少、浓度/设置是多少 | 体积、终浓度及单位 |
| 时间与条件 | 何时做、持续多久、什么条件 | 相对哪个事件开始；时长、温度或仪器条件 |
| 完成标准 / 输出 | 怎样判断这一步结束，产生什么 | 进入孵育；或记录明确的可观察终点 |
| 来源 | 参数依据是什么 | 用户给定、实验室 SOP、引用方法或待核实 |

并非每一步都应该硬塞数值。对适合定量的步骤要求数值与单位；对终点由观察决定的步骤，要求可观察、可复现的判据。诸如“适量”“充分”“按常规”若没有明确参数或可追溯 SOP，就标成待补信息；Agent 不得擅自猜数值。参数还要标明属于 **Protocol 固定值、设计变量还是 Run 实际值**，并保留来源；未知值保持未填写，不能被润色成确定事实。

Agent 通过已有的 Protocol CLI / 同一编辑对象返回结构化步骤和差异，不另开“Agent 草稿页”。系统用确定性校验给出字段级结果，例如 steps[2].duration 缺失、steps[4].target 无法解析、某个模糊短语没有对应 SOP 引用，并提供一个明确的补充问题。校验结果只报告缺项、冲突和下一步，不输出长段泛化建议。校验器可以检查格式、单位、参数归属、样本引用、步骤依赖和必填项；科学上是否适用仍由研究者或明确来源确认，不能靠语气像专家的文字判定。

Protocol 可以先作为不完整草案保存；是否满足执行要求由校验结果推导，不再维护一套冗余的“可执行状态”。发布/冻结时生成不可变版本，修改产生新版本；Run 固定实际采用的版本。Agent 对发布版本先提出字段级差异，确认后才形成新版。

这种做法借鉴 protocols.io 将材料、步骤、子步骤、引用和 troubleshooting 分开组织，以及 Benchling 复用 sub-template 的方式；ISA-Tab 也把 Protocol 引用与具体参数值分开表达。CellPlanner 用一套版本化步骤块库处理这些复用，不另建操作模块系统。[protocols.io Protocol Editor](https://www.protocols.io/help/editor) [Benchling templates 与 sub-templates](https://help.benchling.com/hc/en-us/articles/39939099777933-Configure-Notebook-templates-and-Template-Collections) [ISA-Tab Protocol 与 Parameter Value](https://isa-specs.readthedocs.io/en/latest/isatab.html)[protocols.io Protocol Editor](https://www.protocols.io/help/editor) [ISA-Tab Protocol 与 Parameter Value](https://isa-specs.readthedocs.io/en/latest/isatab.html)

### V1 的明确取舍

- **做**：有限步骤块库、线性 Protocol、Assay 级根步骤块版本引用、设计模板实例化、字段级校验与差异预览。
- **不做**：用户编写模块代码、通用流程图和自动分支调度、Agent 自由生成一整篇不可校验的 SOP、独立的 Agent 规划工作台、对未知科学参数自动补值。超出 V1 流程能力的实验仍可用自定义步骤记录，并清楚标示不能自动校验或排程。
- **验收重点**：Agent 生成的 Protocol 即使尚未完整，也能准确指出每个缺项及其影响步骤；关键参数没有来源时不会被当作事实；用户能从简洁步骤表判断“下一步做什么、对什么做、用什么条件、何时结束”。

## 防止契约把创造性工作锁死

实验设计的关键风险是把“系统建议”误做成“数据不允许保存”。因此要采用 **接口封闭、科学内容开放**：Agent 工具的外层字段、类型、版本和副作用边界必须严格，保证不会误写；实验的科学选择不能被一份固定枚举表穷尽。用户遇到新实验、新参数或非常规步骤时，应能用有类型的自定义字段或自定义步骤先把它清楚记录下来，即便软件暂时不能替它自动计算。

| 检查层 | 例子 | 处理方式 |
|---|---|---|
| 数据完整性 | 输入结构损坏、类型不符、版本冲突、不可解析的修改目标 | 拒绝这次写入，精确指出字段；不部分提交 |
| 操作可行性 | 当前操作缺少实际执行必需值，或选定载体容量不足 | 草案仍可保存；只阻止受影响的冻结 / 排程 / Run 操作，并说明原因 |
| 科学建议 | 可能缺少对照、n 的依据不清、处理与批次可能混杂、方法尚未验证 | 给出适用条件、依据和影响；用户可标记已确认、暂不处理或不适用，不把建议伪装成错误 |

检查规则还要标出它属于产品不变量、实验室自己的约定还是非强制建议，并记录规则版本。只有产品不变量能直接拒绝数据损坏；实验室约定由用户选择启用；科学建议默认不阻断。若用户认可一条建议不适用，记录简短的确认状态即可，不强迫填写一篇“理由说明”。执行安全相关的明确冲突仍可阻止对应操作，但不能因此禁止用户保存设计草案或完整保留原始实验方案。

扩展不依赖改源码：新 assay 或独特步骤可以先用自定义 Protocol 步骤表达；新实验室参数可以建立一个类型化字段（名称、类型、单位/选项、来源、需要填写的阶段）。普通字段即使尚无 semantic_role，也能保存与展示。仅当用户希望软件据此自动算孔数、推导样本数或执行其他机器动作时，才要求该字段映射到已支持的语义与规则。这样既避免未知键导致静默错误，也不要求每个新实验先等产品开发。

为减少未来改动成本，模块和 Protocol 都以不可变版本保存，增加字段默认只影响新版本；旧草案 / Run 保留原义，升级先展示兼容性与影响。遇到当前能力表达不了的设计时，系统应保留用户输入并明确显示“可记录，暂不能自动校验 / 排程”，而不是拒绝或把它改写成近似支持的流程。

验收时除既有的 L929、SA 梯度和生物膜案例，还要加入一个没有现成步骤块的新实验：用户能通过自定义字段和手写步骤存下设计、Agent 能读回并只报告真正无法计算的部分；已有 Protocol 根块版本不因新增步骤块而改变。这样检验的不是系统能猜中所有实验，而是它在扩展能力时不会丢失、曲解或压制新的实验设计。

### 本轮收敛：把所有可复用小步骤纳入步骤块模型

所有可复用操作统一表示为**步骤块 `ProtocolBlock`**，不另建一套仅覆盖常见动作的操作模块库。步骤块可以很小（例如“配制 0.5% GelMA”），也可以由多个连续小步骤组成；Protocol 按顺序引用确切版本的步骤块。若步骤块组合其他步骤块，只允许有序、无环引用，不引入条件脚本或通用工作流引擎。这样小步骤都可复用，数据模型仍只有一种步骤块契约。

每个步骤块保存名称、用途、输入材料、输出材料 / 状态、步骤、参数槽位及参数来源。实例化时只填写声明为可变的槽位；固定参数保留其来源，Run 才记录批次、日期、操作者和实际值。比如某个 GelMA 步骤块可把浓度作为版本固定值，也可把浓度设为待绑定参数；工具不会把例子里的 0.5% 自动推广成所有实验的正确配方。修改配方产生新步骤块版本，已存在的 Protocol / Run 不会被悄悄改写。

Agent 组 Protocol 时优先搜索并引用现有步骤块版本，只返回块顺序、参数绑定和待补项，不重写每个步骤块的长说明；只有找不到合适步骤块时才提出新块供用户保存。界面默认显示块名和一句步骤摘要，展开后才看完整动作、来源和注意事项；打印或执行视图可以按需展开步骤块全文。用户可选中连续步骤“保存为步骤块”，以后在别的 Protocol 中直接插入。

为避免两个独立的通用扩展框架，V1 保持核心科学对象不变；稀有的设计字段用类型化自定义字段补充，不建一套通用的 Assay 模块目录。程序步骤的复用统一走步骤块库。对照、实验单位、样本分配、Assay 与测量指标 `Endpoint` 等影响计算和样本关系的内容仍属于核心模型。

## Agent 写 Protocol 的契约，以及可调用工具的边界

这里的核心任务不是让 Agent 写一篇漂亮的实验方案，而是让它在已声明的结构内组合步骤。Agent 主要做：检索可复用步骤块 → 绑定本次参数 → 调用确定性工具计算 → 生成字段级差异 → 用简短步骤表呈现。现有步骤块能覆盖时只引用 ID 和版本，不复制或重写其全文；没有合适步骤块时才提出一个可校对的新块。

### 步骤写入契约

| 字段 | 规则 |
|---|---|
| 操作 | 用明确动词描述一次操作；一条步骤只表达一个动作或一个有明确边界的连续小过程 |
| 对象 / 材料 | 指向已有样本、材料、容器或显式标记为新输入；禁止用含糊代词 |
| 参数 | 每个参数带值、单位、归属（步骤块固定值 / 本设计变量 / Run 实际值）和来源；未知值保持空缺并附检查项 |
| 时间 / 条件 | 仅在该动作适用时要求；时间须说明锚点，条件须有明确值、范围或来源 |
| 完成 / 输出 | 写明下一状态、产生的材料 / 数据，或可观察的结束标准 |
| 来源 | 参数来自用户、实验室 SOP、文献或计算工具时保留引用；Agent 推测必须标为建议，不能变成已确认值 |

这不是要求每步都填满同一张大表。所需字段由步骤块自身的类型化契约决定；通用步骤只检查动作、对象和适用参数。模糊词如“适量”“充分”“按常规”若没有限定条件或可追溯 SOP，校验器给出字段路径和一条补问，草案仍可保存。完整 Protocol 不应由 Agent 额外附加长篇解释；UI / 导出通过引用展开步骤、来源和必要注意事项。

### 工具分工

| 工具 | 负责什么 | 约束 |
|---|---|---|
| protocol.block.search / protocol.block.get | 找可复用步骤块、读取指定版本和参数槽位 | 只读；不根据相似名称自动替换 |
| protocol.preview_compose / protocol.validate | 展开步骤块、汇总计算工具结果、检查缺项和顺序冲突 | 只读；返回 `issues` 数组（path、code、severity、message、next_action），不写数据 |
| protocol.apply_patch | 将 Agent / 用户确认的字段级增删改写入草案 | 输入是封闭 patch schema，必须带 expected_revision；返回差异与新 revision，不发布版本 |
| plate.layout.preview | 按组别、重复、对照、容器规格等生成候选孔位和容量检查 | 纯计算，不改设计；保留随机种子 / 分配规则，输出孔位映射和限制 |
| calc.solution.preview | 按用户给出的 stock、目标浓度、目标体积和兼容单位计算配液量 | 纯计算，回传公式、单位、输入假设及舍入；缺项则报 issue，不猜输入 |
| protocol.block.save_version | 将已校对步骤保存为新的可复用步骤块版本 | 写入前显示来源与字段；不覆盖旧版本，不自动发布为通用实验室事实 |

工具名是接口设计建议，不代表原型已实现。计算类工具负责数值，不负责选择科学假设；步骤块描述人要执行的操作，不在内部调用任意代码。Agent 只能把工具结果作为带来源的派生值写入候选 patch。用户确认后，写入草案；发布、冻结或影响科学设计的变更按既定确认边界处理。

### 防止 Agent 冗长与漏项的实际流程

1. Agent 读取当前设计和 Protocol 版本，先搜索现有步骤块。
2. 找到步骤块就引用其精确版本，只填写可变参数；需要板图 / 配液时调用对应 preview 工具。
3. 找不到步骤块时，Agent 用短结构提出新块，标出未确认字段与依据，不输出长段泛化 SOP。
4. validate 返回具体缺项、冲突和是否影响本次操作；用户看同一 Protocol 编辑界面的步骤摘要与差异，决定补充或暂存。
5. 用户确认后应用 patch；发布版和执行 Run 固定引用的步骤块、参数与来源。

因此“模块化”主要减少重复生成和重复阅读：复用时是简洁引用，展开时才看细节；“工具化”则让孔位与数量计算可复核。两者共享同一套来源、版本和参数契约，但不是同一类对象或副作用。
## 用既有实验记录做快速桌面走查

以下只用现有的 L929 与 SA 记录做结构模拟，不代表软件原型已实现，也不补写原记录没有的实验参数。来源见 [2026-11-02 设计流程走查](2026-11-02-cellplanner-design-flow-walkthrough.md)。

### L929：GelMA-ZnO 多检测设计

- 核心设计保存三种处理：完培对照、GelMA 浸提液 E1、GelMA 浸提液 E2（记录约为 CuCl₂ 终浓度 10 μM）。
- CCK-8 是四类分配（空白、完培、E1、E2）× 每组 6 孔 = 24 个分配孔；空白为无细胞检测对照。D1/D3/D7 回到同一批孔测量，测后吸液、补液。
- 活死染色为 D1/D3/D7 三块独立 12 孔板，每个时间点三组、每组 3 孔；每板终末检测。划痕和接种密度校准仍是各自的 Assay，不被并入 CCK-8 步骤。

Protocol 只需引用已保存的“同孔重复检测 / 测后换液”步骤块并绑定时间点；若实验室有经确认的 CCK-8 具体操作，也可再引用对应步骤块。plate.layout.preview 可核对 CCK-8 的 24 个分配孔、活死每板 9 个实验孔；具体坐标只有在记录或用户给出时才确定。这里的边界是：同孔复测、终末板、实验单位和时间锚点属于设计 / 样本关系；试剂体积、孵育时长、读板设置属于 Protocol 参数。摘要未给出的具体参数应列检查项，不能由 Agent 补齐。

### SA 铜离子梯度：计算器与步骤块分工

- 记录为 4 个处理条件、每条件 3 孔、两块 6 孔板；每孔总体系 550 μL，处理液 50 μL。
- calc.solution.preview 按终浓度 = 母液浓度 × 50 / 550 复算：1 M 母液约 90.9 mM，10 mM 约 909 μM，100 μM 约 9.09 μM。输出同时保留输入、单位和公式；PBS 对照不参与 CuCl₂ 稀释计算。
- 步骤块表达“按指定组别加入 50 μL 处理液”等实际动作；计算器产出的终浓度作为带来源的派生参数绑定进去，不把公式复制成 AI 长文。
- 原记录中 P1/P2 的剂量分布与板号重合，应作为可能的板位混杂提示；9 月 2 日每孔 550 μL 与 9 月 4 日取样 1 mL 的冲突则保留为待核实 issue。layout / calculator 工具不改写历史映射，也不替用户解释冲突。

### 和旧方案相比，是否更清楚？

更清楚，主要因为职责不再混在一个“万能模块”里：设计核心回答“比较什么、n 是谁、样本如何分配、何时测”；步骤块回答“具体做什么”；layout / calculator 工具回答“可确定地怎么算”。Agent 复用步骤块和绑定参数即可生成短步骤，缺失时指出具体字段，不必重新讲一遍原理或猜参数。

剩余的真实风险是步骤块过碎或重复。控制方式不是禁止小块，而是让步骤都可保存、但不强迫每一步单独保存：先搜索现有步骤块，支持把连续步骤组合；编辑器默认折叠组合块，显示简短摘要；共享范围、来源和版本可见。下一步验收应实际模拟“创建新步骤块 → 组合 Protocol → preview 工具结果 → 保存草案”，并用上述已知数字断言 24 个 CCK-8 分配孔、每个活死板 9 孔和 SA 三个浓度复算值；本次仍是文档级桌面走查。

## 最终对象形态：Protocol 与微步骤共用一种可递归组合的对象

Protocol 是面向用户的顶层操作方案；它与步骤块使用同一套版本化内容模型 `ProtocolBlock`，不再维护第二种步骤对象。一个 ProtocolBlock 可以是原子步骤，也可以是引用子块的组合；被实验设计直接引用时称 Protocol，被其他步骤块引用时称子步骤块。CCK-8 方法因此既能独立作为一份 Protocol，也能作为更大实验流程中的一个组合步骤块。

每个版本只需表达四类东西：用途和名称、输入材料 / 条件、输出材料 / 状态、参数槽位与有序内容。内容可以是一个动作，也可以按顺序引用其他 ProtocolBlock 的精确版本并绑定参数。父块引用子块，不复制子块正文；同一个 GelMA 浸提液制备块可以被 CCK-8、活死染色或其他方案复用。组合引用必须无环；调整子块不自动改写父块，升级时由用户查看差异并生成父块新版本。

层级不设固定的两级或三级：用户可继续把 CCK-8 展开成铺板、处理、加试剂、孵育、读数等步骤块，也可将若干块重新组合。UI 默认折叠为可读的组合标题，需要执行时再逐层展开。所有块共享同一字段与版本机制，只维护一套步骤块库。

### 步骤块怎么切

模型允许任意拆分，但建议把最小步骤块定为**具有明确目的、输入和输出，能独立复用或单独确认的一段操作**。例如，若它有明确来源和参数，“制备 GelMA 浸提液”适合作为一个子块；把“拿起枪头”这类没有独立输入输出或复用价值的动作拆成单块，通常只会增加导航和版本维护。用户仍可在需要时继续细拆，不受固定粒度限制。

一个组合块可以保留顺序和子块引用；只有本身需要变化的值才暴露成参数槽位。父块可把子块参数显式映射、固定或继续向外传递；不得有隐式覆盖。若父级绑定、子块固定值和设计条件互相冲突，返回带字段路径的检查项，不按隐含优先级选择。若不同实验的浸提比例、时间或温度不同，应在使用时绑定到明确槽位，来源未给出的仍显示待确认。来源记录未提供的 GelMA 制备细节不能仅凭“0.5%”自动推导。

### 用生物安全性实验表示复用

同一份“制备 GelMA 浸提液”不应分别复制进每项检测。更清楚的组合关系是：

- **生物安全性实验设计**：保存细胞、处理组、实验单位、样本分配、时间点和各检测终点。
- **浸提液制备块**：计划阶段声明预期产物及来源关系；执行时才生成具体、有来源的浸提液材料实例，供一个或多个 Assay 使用。
- **CCK-8 Protocol**：可独立作为完整操作方案；内部继续引用铺板、处理、读数等步骤块。
- **活死染色 Protocol**：按它自己的样本使用与终末时间点引用所需步骤块。

如果当前方案中浸提液是 CCK-8 和活死染色共同使用的同一份材料，父级生物安全性流程把它制备一次，再把输出关联到两个检测；如果实际是分别制备，则建立两个执行实例。系统不能仅凭相同材料名称假定它们是同一份样本。CCK-8 的独立 n、重复孔和 D1/D3/D7 同孔测量仍由实验设计核心表达，不塞入 ProtocolBlock。

因此 Agent 写出的单份 Protocol 展开后是一棵**可折叠的引用树**，而所有 ProtocolBlock 共享引用构成无环图（DAG）；同一步骤块可被多个父块引用，不复制长篇文字。工具层提供同一对象的 search / get / compose-preview / validate / save-version；铺板排位和浓度换算继续由独立、纯计算的工具提供结果，不建立步骤块与 Protocol 两套读写入口。

## 变体与参数变化：复用原块，不因小改动复制 Protocol

可递归组合解决“步骤怎么复用”，还需要明确“复用时怎么改”。这里不再造一套新的协议类型：仍以 ProtocolBlock 为基础，另记录它在某次方案中的参数绑定；用户显式保存时，才把一组差异命名为可复用变体。

数据上区分“块的版本”和“块的一次使用”：使用记录引用块版本并绑定本次参数。仅参数不同且想复用时，保存的是带名称的参数覆盖（基块版本 + 参数差异），不是一份复制的 Protocol；它可以被其他 BlockUse 引用。若流程结构也改变，则仍用同一种 ProtocolBlock 表示派生版本，并以基块引用和子步骤差异表达，不引入第二种片段体系。

### 三种变化按影响处理

1. **本次实验的参数绑定**：步骤和顺序不变，只改变已声明的槽位，例如浸提时长、温度、材料与培养液比例或目标工作浓度。记录为这次 BlockUse 的绑定，不新建碎片，也不改基础 Protocol。
2. **希望以后重复用同一套条件**：用户选择“保存为变体/常用条件”。变体只存对基础块的稀疏覆盖（基础块精确版本 + 被改参数 + 来源），不复制步骤树。例：同一 GelMA 浸提液制备块，保存两套经用户确认的浸提条件；CCK-8 和其他实验都可引用其中一套。变体有自己的版本，修改基础块不会静默改变它。
3. **操作顺序或步骤内容改变**：若改变仍属于同一用途，保存为基块的派生变体，记录新增、替换或移除的子块及理由，保留原块引用和差异预览；若用途已不同或变化大到无法简洁说明差异，再创建独立 ProtocolBlock。是否拆分由可复用目的决定，不按改了几行判断。

Agent 默认只为当前方案绑定参数；不得因为一次微调自动新增碎片或变体。发现相同条件可能复用时可以建议保存，但由用户决定。UI 主要呈现“基于哪个步骤 + 本次改了哪些值”，继承内容默认折叠；执行清单展开最终生效值和来源。

### 浓度变化要表达清楚是哪一种

“浓度”不能作为一个含义不明的数值字段。至少区分：输入材料/母液浓度、配制目标浓度、按配液计算得到的工作浓度、实际测得浓度。它们分别保留单位、物质/材料对象、浓度基准及来源。比如目标工作浓度变化，只改变本次参数绑定；配液工具根据母液浓度、目标浓度、最终体积等明确输入计算加样量，并回传公式/输入/单位。若最终浓度是检测得到的，则作为执行观察值记录，不能被目标值覆盖。

GelMA 浸提液场景中，浸提条件和后续对细胞的稀释/暴露浓度属于不同步骤的参数。计划里可以表达“多个 Assay 预期共用一次制备”或“各自制备”；只有开始执行后才创建有来源的实际材料实例并关联各 Assay。若执行中发现实际分开制备，记为不同实例/偏差，不把计划关系伪装成事实。资料未提供的浓度基准或配制条件仍待确认，计算器不替用户推断，Agent 也不把目标值写成已得到的产物事实。

## 落地边界：允许深入拆分，不让用户被层级拖住

这些理想能力应作为模型的表达上限，而非用户必须遵守的设计纪律。任意层级可拆分不等于每一步都要单独建块；默认只让用户看到完整方法和少量关键步骤，只有需要复用、独立确认、独立改参数或追踪产物时才建议抽成子块。用户可随时把已有段落提升为块或重新组合，不强迫先规划完所有层级。

数据模型也采用渐进结构：

- **ProtocolBlockVersion** 保存可读步骤、可选参数槽、预期输入/输出及精确子块引用。没有参数槽的普通文字步骤仍可保存、执行查看；它只是不参与自动换算或强校验。
- **BlockUse** 表示设计或父块中的一个具体使用位置，具有稳定 ID，引用某个精确块版本并绑定本次条件。同一块版本被引用两次就有两个 BlockUse；单次改浓度、温度或时间只改变这次绑定，不复制块。
- 用户明确要复用一组条件时，保存为基于原块版本的命名参数覆盖；这不是另一份 Protocol 正文。步骤结构变化则创建可查看差异的派生版本；只有目的或逻辑已明显不同，才拆成独立块。
- 计划产物与执行产生的实际材料分开。计划可先保存“预期来源/共享关系”，执行后再记录批次、实际样本、实际浓度和偏差。不能因为模块声明了输出，就把计划值写成实验事实。

这套机制的价值不在于把所有文本都变成可计算工作流，而在于：文字步骤保持开放；有明确单位、输入和输出的槽位可以被确定性工具计算；有实际来源的材料关系才能支撑追溯。缺少信息时保存草案并指出哪个具体动作受影响，不能因模型不认识新实验就拒绝保存。

### 用最小闭环验证是否值得继续加复杂度

先让一个用户完成：创建生物安全性实验 → 组合 GelMA 浸提液制备与 CCK-8 → 将同一预期产物关联到另一项检测 → 改一次工作浓度并计算配液量 → 选择是否保存为常用条件 → 冻结执行版本并记录实际制备/偏差。验收重点是内容没有复制、参数来源说得清、未确认值不被猜填、执行数据不覆盖计划。若此流程需要用户理解很多新名词，优先简化界面或把字段放入高级详情，而不是增加更多对象类型。

## Agent 在真实使用中的操作契约

Agent 的正确性不能靠“提示词写仔细一点”保证。它需要始终围绕当前选中的项目/设计、确切版本、来源证据和有限工具操作；用户说的话用于理解意图，不作为绕过结构校验或版本约束的通行证。

### 一次修改的闭环

1. **先解析目标，不先写。** 从当前界面上下文取 project/design ID 和 version；从口语目标解析“要改哪个对象、改成什么、是草案还是已执行记录”。同名 Protocol、实验或样本必须用稳定 ID/版本确认。多个匹配且会影响结果时，不可凭名字或最近使用自动挑一个。
2. **把证据和推断分开。** 每个值携带来源标签：用户原话、导入原文位置、已引用 Protocol 版本、确定性计算、Agent 建议或未知。导入记录里的多种说法先并列为冲突证据；不能因为文件日期较新就默认它覆盖旧计划，除非记录明确说是修订。
3. **只生成窄提案。** Agent 调用 `propose_patch` 提交字段路径和预期版本，不重写整份设计或 Protocol。系统返回字段差异、影响对象、重算值、未决项和诊断。未知字段不静默丢弃；不支持的操作返回可解释错误。
4. **计算与兼容性由工具负责。** 孔位、配液、容量和相对时间使用确定性工具；Agent 不口算后伪装成校验结果。组合 Protocol 时检查子块声明的输入/输出与父流程需求。只有规则明确证明冲突时才阻断；“没有兼容性资料”应标为未验证，不等于不兼容。
5. **只问当前动作需要的问题。** 草案缺信息仍可保存。只有当用户要求的具体计算/执行依赖缺项时，返回 `needs_input`，指出缺哪个字段、为何需要、补上后影响什么；一次优先问最能改变结果的一项，其余仍留在草案。
6. **先展示结果，再提交有后果的修改。** 提案清楚列出“将改变什么/不会改变什么”。涉及独立 n、组别、主要结局、浓度目标、Protocol 步骤或已批准设计时，要求用户确认；只读查询、预览和明确输入后的纯计算可直接返回。提交时带 `expected_version`，冲突就重读并重新提案，不盲目重放旧写入。
7. **核对回执。** 写操作返回对象 ID、新版本、字段路径和状态。Agent 只有确认回执后才能说“已修改/已创建”；超时或不确定回执不能再次创建 Run、板或样本，应先按 idempotency key 查询结果。

工具回执应机器可读且短：`status`（如 previewed / proposed / committed / needs_input / version_conflict）、目标 ID 与版本、字段级 diff、受影响计算、issues、unresolved fields、下一步问题和写入回执。自然语言说明负责让用户看懂，不承载唯一事实。

### GelMA / CCK-8 的口语输入如何落地

用户说“用 GelMA 浸提液做生物安全性，安排 CCK-8，再加活死染色”时，Agent 先从现有 Protocol 库找候选块并显示用途/版本；若没有可靠匹配，则创建草案块而不是编造完整 SOP。它可提出“两个检测是否共用同一批浸提液”的默认待确认关系，但不能按相同材料名自动判为同一份。实验组、独立 n、终点和时间点属于设计对象，不能被藏进 CCK-8 步骤。

如果用户随后只给出新的目标工作浓度，Agent 将它绑定到该次处理/检测使用；先检查浓度基准、母液浓度、最终体积是否足以计算。缺项时仍可保存设计，但配液计算明确返回 `needs_input`。用户要求以后复用这套条件时才保存命名参数覆盖；不会为这次浓度改动复制一份 CCK-8。用户改了铺板/加样的操作顺序时，Agent 提交可比较的派生 Protocol 版本，并重新预览孔位、用量及相关检测影响。

### 必须通过的 Agent 故障用例

- 搜到多个同名或相近 Protocol：列出用途与版本，不误选，也不覆盖别的块。
- “n=6”没有说明单位：不解释成 6 个独立样本；仍能保存草案，并只在计算独立样本数或执行时追问。
- 同一材料名但制备批次不明：不自动合并样本来源；计划层保留待确认的共享关系。
- 目标浓度与实测浓度同时出现：前者作为参数，后者作为观察值，两者不互相覆盖。
- 母液/目标浓度/最终体积不全：不猜数，不给貌似精确的加样量。
- 旧记录计划与执行时间冲突：保留两条证据并询问是改版还是偏差。
- 方案准备期间用户又编辑了设计：旧 `expected_version` 提交失败，刷新上下文后重新生成差异。
- 用户要求“把步骤写完整”但来源没有剂量/时间/温度：产出结构化待确认槽和已有步骤，不填常见值凑完整。
- 保存或创建动作遇到超时：按幂等键查询回执再决定是否重试，防止重复创建。

因此需要验收的不只是“LLM 生成的文字看起来合理”，而是目标对象是否选对、来源是否保留、修改边界是否窄、派生结果能否重算、未确认信息是否如实暴露，以及失败重试是否不会制造重复事实。
