# CellPlanner 设计基线与术语表

日期：2026-11-03
状态：当前产品设计的统一摘要；基于真实实验记录的桌面走查与方案讨论，尚未实现为运行时代码。本文用于统一术语和边界，早期研究文档中的探索性叫法不自动视为 V1 决定。

术语的规范写法以项目根目录 [`CONTEXT.md`](../../CONTEXT.md) 为准。本文用于说明设计依据与案例；若本文仍出现旧称，以 `CONTEXT.md` 的规范术语映射为准。

## 一句话定位

CellPlanner 帮研究者把研究问题整理成清楚、可调整、能执行和追溯的实验设计；Agent 理解意图、查找和组合方法、提出修改，确定性工具负责计算，研究者保留关键科学决定。

核心不是让 Agent 写一篇很长的实验方案，而是让用户少从空白开始、少重复录入，并能看清每一步怎么做、哪些信息还没确认、哪些结果是计划或计算而非实际观察。

## 设计原则

1. **界面简洁，内部关系严谨。** 用户日常看到项目、实验、设计和执行批次，不必学习内部对象名。复杂样本流向、孔板和参数详情按需展开。
2. **草案允许不完整。** 先显示已知事实；只在缺项影响当前计算或操作时追问。未知值不以“常用值”补齐。
3. **科学内容开放，工具契约严格。** 新实验可用自定义字段和步骤记录。只有明确声明且输入充分的结构化字段才参与自动计算；新颖或未验证不等于无效。
4. **研究者做科学选择，软件做可复核工作。** 组别、独立实验单位、主要比较和关键参数不能由 Agent 擅自决定；孔位、体积、配液和相对日程由确定性计算完成。
5. **计划与事实分开。** 计划里的预期样本、预计产物、目标浓度和预排孔位不是已经发生的执行事实。
6. **同一内容只保存一份。** Protocol 通过精确版本引用组合；参数覆盖和结构变化可追溯，不复制整篇步骤。

## 全流程对象

```text
项目 Project
└─ 实验 Experiment（一个科学问题或目标）
   ├─ 设计版本 DesignVersion（研究者准备如何回答问题）
   │  ├─ 主要比较、因素与组别
   │  ├─ 实验单位、独立 n、重复与样本分配计划
   │  ├─ 一个或多个检测 Assay、测量指标 Endpoint、时间点
   │  ├─ 对各检测引用的根步骤块版本（界面称 Protocol）
   │  └─ 计划日程、材料需求与可选载体/孔板预览
   └─ 执行批次 Run（一次真实执行）
       ├─ 固定引用设计版本和实际采用的根步骤块及所有子块版本
      ├─ 实际样本、容器/孔位、事件、读数与偏差
      └─ 原始观察值及其派生结果
```

步骤块库与实验设计相连，但不是第二份实验计划。Protocol 是根步骤块在检测中作为完整方法展示时的名称，不是第二种步骤内容类型：

```text
步骤块版本 ProtocolBlockVersion（共享、不可变版本、无环引用）
    ↓ Assay 顶层引用一个根版本，界面显示为 Protocol；子块按确切版本递归引用
DesignVersion 为每项检测绑定参数
    ↓ Run 创建时冻结完整引用树
执行中记录实际值、实际材料和偏差
```

整个步骤块库是无环有向图（DAG）：同一块可以被 CCK-8、活死染色等多个方案引用；打开一份 Protocol 时，界面把根步骤块展开为便于阅读的步骤树。系统不要求用户先把整套树拆到最底层，也不允许循环引用。

不增加 Study 层。一个实验可以包含多个 Assay；研究问题或阶段判断确实不同，才拆成不同 Experiment。没有孔板的动物、组织、菌液或影像实验不生成空白孔板对象。

## 规范术语

下表是产品文案与 Agent/CLI 的统一用词。界面优先使用“显示名称”；代码、存储和工具接口用括号内标识。一个中文词不再同时代指多个对象。

| 规范中文 | 英文/内部标识 | 准确定义与使用边界 |
|---|---|---|
| 项目 | `Project` | 一组相关实验的组织容器。 |
| 实验 | `Experiment` | 围绕一个科学问题/目标组织的工作；可有多个设计版本和执行批次。不要拿它指单次 Run。 |
| 实验设计版本 | `DesignVersion` | 对实验问题的结构化回答计划，包含比较目标、组别、实验单位、Assay、时间、样本分配及各 Assay 的根步骤块版本等。界面可简称“设计”。Run 固定引用某个确切版本；修改已确认设计不覆盖旧版本。 |
| 研究问题 | `research_question` 字段 | 用一句话说明实验想回答什么；它不等同于分组或统计比较。 |
| 比较目标 | `Comparison` | 明确比较哪些组别/条件、针对哪个测量指标，以及是组间比较还是因素效应。组别存在不代表比较目标已明确。 |
| 执行批次 | `Run` | 设计的一次实际执行；冻结实际采用的根步骤块及所有子块版本。多次 Run 不自动等于多个独立 n。 |
| 因素 | `Factor` | 研究者操纵或比较的变量，如处理类型或剂量；每个因素有水平。 |
| 水平 | `Level` | 因素的具体取值，如某处理条件下的剂量值。 |
| 处理条件 | `Condition` | 一个实验单位实际接受的因素水平组合。 |
| 组别 | `Group` | 按处理条件分配和呈现的一组实验单位；可标记对照角色。不要把“材料”“板”当成组别。 |
| 对照角色 | `ControlRole` | 说明某组在本实验中承担的参照用途，如未处理、溶剂、空白或阳性对照；具体是否需要及如何设置由研究问题和方法决定。 |
| 实验单位 | `ExperimentalUnit` | 实际被独立分配到处理条件的单位。可能是供者、动物或独立培养体系，具体由分配和材料关系决定；不能仅凭孔、视野或读数数量决定。 |
| 独立实验单位数 | `experimental_units_per_group` / `n` | 每组独立接受处理的实验单位数量。若分配单位不清楚，不显示确定的 n。ARRIVE 将实验单位定义为可独立接受干预并能被分到不同处理组的实体；把其下属细胞、切片或重复测量误当成 n 会造成伪重复。[ARRIVE 2.0](https://arriveguidelines.org/arrive-guidelines/study-design/1b/explanation) |
| 技术重复 | `TechnicalReplicate` | 同一实验单位下的重复孔、视野或读数等测量层级。是否属于技术重复取决于样本和处理分配关系，不取决于容器外形；不能自动加到独立 n。 |
| 重复执行关系 | `repeat_of_run_id`（可选关系） | 表示本次 Run 是按既有设计再次执行；它本身不能证明样本来源或实验单位彼此独立。每个 Run 仍单独记录实验单位与来源。 |
| 检测 | `Assay` | 一项测量活动，如 CCK-8 或活死染色。定义它用什么样本、在何时测、使用哪个根步骤块版本和何种载体。检测方法本身不是测量指标。 |
| 测量指标 | `Endpoint` | 希望检测/比较的结果，如活力指标、图像闭合率或菌落计数；可标记主要/次要及单位。 |
| 时间点 | `Timepoint` | 相对于明确事件的测量或操作时间，例如“处理后 24 h”；记录锚点、偏移量和必要时间窗，不只写 D1/D3。 |
| 原始观测值 | `Observation` | 执行中直接取得的读数、图像或记录，不等于归一化或计算后的结果。 |
| 执行事件 | `ExecutionEvent` | Run 中记录一次实际发生的操作，以及已知的对象、时间、操作者、结果或偏差；步骤定义或引用本身不代表操作已发生。 |
| 派生结果 | `DerivedResult` | 从原始观测值按明确公式/版本计算的结果；与原始观测值分开保存。 |
| 操作方案（Protocol） | 顶层使用角色 | 某个根步骤块版本在 Assay 中作为完整方法显示的名称/角色；不是第二种步骤内容类型。 |
| 步骤块 | `ProtocolBlock` | 可复用操作内容的唯一类型，可表示一个原子步骤或一组有序子步骤。中文不再混用“模块、片段、微流程”。 |
| 步骤块版本 | `ProtocolBlockVersion` | 不可变的块版本。组合块引用子块的确切版本；修改已引用内容时通过新版本和差异表达。 |
| 操作步骤 | `Step` | 步骤块内部的动作说明。普通文本步骤可保存和阅读；只有明确结构化的字段才用于自动计算。 |
| 参数槽位 | `ParameterSlot` | 步骤块声明的可变输入，带类型、单位/浓度基准、适用时机和来源要求。 |
| 步骤块使用 | `BlockUse` | 某设计或父步骤块中的一次具体引用；有独立稳定 ID，指向确切版本并携带本次参数绑定。同一版本被引用两次，表示两次使用位置。 |
| 本次参数绑定 | `ParameterBinding` | 某个 BlockUse 对参数槽填写的值。一次性改浓度、温度或时间只产生本次绑定，不创建新步骤块。 |
| 条件预设 | `ParameterPreset` | 用户明确保存的一组可复用参数覆盖，引用基块确切版本，不复制步骤正文。 |
| 派生步骤块版本 | `ProtocolBlockVersion`（带 `based_on_version_id`） | 操作顺序或子块结构改变后形成的新步骤块版本，记录基版本和差异；仍是同一种步骤块版本类型。 |
| 样本来源材料 | `SourceMaterial` | 供实验单位或样本派生的起始材料，如供者来源、培养物或组织。不能与一次实际检测样本混为一谈。 |
| 样本材料 | `Sample` | 实际存在、可追踪的生物材料实体。设计阶段先存数量和分配规则，不伪造实际 Sample ID。 |
| 分样 | `Aliquot` | 从一个样本中分出的材料部分；保留父来源和去向。 |
| 样本分配计划 | `SampleAllocation` | 计划层的内部关系：哪些组/来源材料预计供哪个 Assay、时间点或分样使用。界面默认翻译为“样本去向/来源”。 |
| 计划产物 | `PlannedOutput` | 步骤块执行后预期得到的材料/状态。设计时仅是预期；执行后才建立实际材料实例。 |
| 实验载体 / 孔位 | `Container` / `Well` | 实际或计划使用的板、皿、管等物理载体及位置。载体不等于实验单位。 |
| 计划布局 / 实际映射 | `PlannedLayout` / `ActualMap` | 设计阶段的排布预览与执行中实际使用的位置映射，必须分开。 |
| 参数基准 | `ConcentrationBasis` 等 | 明确浓度针对哪种材料、是母液值/目标值/计算工作值/实测值以及单位。不能只存一个无语义的“浓度”。 |
| 设计检查项 | `ValidationIssue` | 结构、操作前提或科学建议的可定位反馈。每项带级别、对象/字段、依据、影响和下一步；不要统称“错误”。 |

### 不再混用的旧叫法

- 口语中的“实验方案”经常含糊：指科学问题和分组时写“实验设计”；指如何操作时写“Protocol/操作方案”。
- 作为程序步骤复用的东西统一叫“步骤块”。不再把同一对象轮流称为 Protocol 模块、操作模块、片段或微步骤库。
- `module.*` 是早期“设计字段扩展”提案，不是步骤块接口，也不是当前 V1 必做能力。若未来需要通用字段扩展，单独评估。
- 不以“生物学重复”一个词表示所有 n。优先写“每组独立实验单位 n=…；每单位技术重复…；独立 Run …轮”。资料不足时只陈述已知的孔数/材料数。
- “计划产物/预期共享”不是“实际样本/已共用”；“目标浓度”不是“测得浓度”；“可执行”是校验引擎计算出的状态，不是 Design 生命周期状态。

## Protocol 的拆分、组合与参数变化

1. **对象只有一种。** 步骤块可为原子内容，也可引用有序子块。CCK-8 可作为完整 Protocol 使用，也能被更大的生物安全性流程引用；不另建一套“CCK-8 模块”类型。
2. **支持继续拆分，不鼓励无意义拆分。** 可复用、可独立确认、有明确目的/输入/输出/版本价值时适合抽块。诸如“拿起枪头”通常留在步骤描述里，除非它确实需要单独复用或审计。
3. **复用引用，不复制正文。** 每条引用钉住精确子块版本；组合无环。升级子块不会悄悄改变父块或已有 Run。
4. **小改动先绑定。** 本次实验改变条件或目标浓度，保存为 BlockUse 参数绑定。用户想反复用这组值时，再保存条件预设。若步骤顺序/内容改变，生成可比较的派生版本；用途或逻辑明显不同才新建块。
5. **参数含义显式。** 目标浓度、母液浓度、计算值、实测值分开；配液计算由纯计算工具完成，并返回输入、单位、公式版本和结果。缺参数时不猜算。
6. **设计与执行分层。** 设计层记录预期输入、输出和样本关系；Run 才创建实际来源材料、样本 ID、孔位、实际参数、读数和偏差。

例：生物安全性设计可引用一次“制备 GelMA 浸提液”步骤块，再让 CCK-8 和活死染色分别引用同一预期产物。如果实际只制备了一份，则 Run 中创建一个实际材料实例并连到两个 Assay；如果分别制备，则建立两个实际实例。不能只因名称相同就合并，也不能把设计时的预期当作已发生事实。

## Agent 怎样可靠地理解和操作

Agent 的正确性不能靠提示词单独保证。它只通过有限、结构化、可审计的工具操作当前对象，不能直接重写整份设计或任意修改数据库。

### 操作次序

1. **读取上下文：** 获取当前 project、experiment、design ID/version 和用户选中的 Assay；缺少上下文时先搜索。名称相近不等于同一对象。
2. **解析意图：** 把用户请求映射到明确目标和字段变化。每个值标明来自用户、来源记录/Protocol、确定性计算、Agent 建议或未知。
3. **读取精确方法：** 搜索候选步骤块，按 ID、用途和版本选择。多个候选会产生实质差异时，列出差别并询问；无可靠模块时保留为自定义草案，不编造完整 SOP。
4. **提出窄修改：** 只提交字段路径及预期版本，返回差异，不发送整份对象覆盖。协议组合检查明确的输入/输出兼容性；未知兼容性标“未验证”，只有有依据的已知冲突才阻断。
5. **调用计算与检查：** 板图、容量、稀释和时间表交给确定性工具；保存/执行前按目标动作校验。计算结果保留输入与公式，不被模型口算替代。
6. **处理缺项与冲突：** 草案可以不完整；只阻止依赖该字段的当前操作。优先问一个会改变设计或结果的问题，其余作为可定位的待确认项。冲突证据并列保留，不能静默合并。
7. **提交并核对：** 用户明确要求且目标清楚的草案小改动可直接提交并回报差异；更改组别、n、测量指标、关键处理参数、解决来源冲突、冻结设计或创建 Run 等高影响动作应先确认。提交带 `expected_version` 和幂等键；冲突则重读再提案，超时则查回执，禁止盲目重试。

工具输出至少使用稳定字段：`status`、目标 ID/version、`diff`、来源、计算结果、`unresolved`、诊断和提交回执。可读说明只解释这些结果，不承载唯一事实。建议工具边界：

| 工具组 | 读写 | 责任 |
|---|---|---|
| `design.get / design.preview / design.validate` | 只读 | 读取当前设计、派生数量/布局/日程、按保存或执行目标返回问题。 |
| `protocol.search / protocol.get / protocol.preview_compose` | 只读 | 找到确切步骤块版本，展示组合和参数绑定，不自动写入。 |
| `design.propose_patch` | 只读提案 | 接收字段级变化与 `expected_version`；返回差异、重算、问题及确认要求。 |
| `plate.preview / solution.calculate` | 只读计算 | 输入完整结构化数据，返回可复核排布/数值；不能缺值猜算。 |
| `design.commit_patch / protocol.save_version` | 写入 | 只提交已展示的提案/新版本，返回 ID、版本与回执。 |
| `run.create / run.record_event` | 写入 | 冻结设计与 Protocol 清单，记录实际执行、观察值和偏差。 |

### 最小 Agent 验收集

- “n=6”未说明单位：不猜作 6 个独立样本；仍可保存草案，说明目前确认的是 6 个孔或 6 个材料单位。
- 多个同名 Protocol：不凭名字自动选版本。
- 同名 GelMA 浸提液：不默认是同一份实际材料。
- 只改目标浓度：不复制步骤块；母液浓度或终体积缺失时配液工具返回缺项。
- 输入旧计划与执行记录冲突：保留原文位置和两种解释，问这是计划改版还是实际偏差。
- 用户在 Agent 准备提案时又改设计：版本冲突后刷新上下文，不覆盖新修改。
- 工具写入超时：查同一幂等回执后再决定下一步，不能重复创建 Run。
- 找不到适配的新步骤：允许新增自定义文本块并标出未验证字段，不拒绝保存。

## 界面与使用节奏

- 主画布按“研究问题/主要比较 → 组别矩阵 → Assay 卡片和时间线 → 最重要的待确认项”组织。
- 默认只突出一个当前关键问题；次要事项折叠，用户仍可直接编辑表格、批量粘贴或让 Agent 提议修改。
- 样本流向只在分样/跨 Assay 共用时展开；板图只在检测确实使用实体载体时出现。
- Protocol 默认展示组合标题和少量关键步骤；更深层子块、来源、参数和注意事项按需展开，不要求用户先管理整棵递归树。
- 不单设 Agent 草稿页。Agent、CLI 和界面操作同一 Design；Agent 提案以差异显示，可撤回/另存版本。
- 提示分为“阻断当前操作”“需要研究者确认”“建议检查”。未知/不适用不是错误；未能判断时说“无法检查”，不伪装通过。

## 生命周期与事实保护

- DesignVersion 可为草案或已确认版本；是否能启动某个 Run 由校验结果推导。“可执行”不另存为一个生命周期状态。确认版本被 Run 引用后保持不变；修改产生新版本。
- Run 有自己的计划中、进行中、已完成或已中止状态；执行中的偏差记录到 Run，不回写覆盖 DesignVersion。
- 导入旧记录时先选择用途：复制成新设计、重建历史计划、或补记已执行 Run。来源段落和冲突证据保留；确认解释后追加，不覆盖原文。
- 计划阶段只建数量、分配规则、相对时间和逻辑位置；实际样本 ID、实际孔位和观察值在 Run 中生成。

## 建议 V1 范围与明确不做

**V1 基线：**项目/实验/设计版本/Run；比较目标、组别、实验单位与 n 的依据；多 Assay 和各自的测量指标、时间、样本分配；递归 ProtocolBlock 定义、稳定的 BlockUse 引用和显式参数绑定；板图和配液的确定性预览；字段级 Agent 提案、校验、提交与执行记录。参数预设、模板升级建议和复杂树编辑延后到基本复用闭环验证之后。

**暂不做：**为了“以后可能有用”建立完整样本库存、通用本体、任意脚本/公式工作流、每个动作都必须模块化、全学科科学规则大全、自动替用户确定样本量/剂量/终点。统计/功效分析、设备自动化和更多实验类型，等真实用例证明需求后再加入。

## 从当前原型渐进迁移

设计文档定义的是目标语义；不要求一次重写当前数据库或破坏已发布的 CLI 契约。建议按以下顺序落地：

1. **兼容旧 Protocol：**先把现有 Protocol 正文包装成一个根 `ProtocolBlockVersion`，正文保留为普通文本 `Step`，保留原 ID、版本和来源；不要求一开始拆解所有旧方法。
2. **建立引用与参数边界：**新增稳定 `BlockUse` ID、精确版本引用和显式 `ParameterBinding`；旧字段可由兼容层映射到根块版本，迁移期间不做无提示的破坏性重命名。
3. **跑通一个多检测闭环：**用 GelMA 浸提液 + CCK-8 + 活死染色验证预期产物、共享/分样、确定性用量计算和 Run 实际事件；结构变更前后均能还原旧版本。
4. **再扩展编辑能力：**基本闭环稳定后再加参数预设、模板实例化、升级建议和更深层编辑。数据模型允许递归，不意味着第一版要实现复杂树编辑器。

## 用真实案例验收，而不是冻结理想模型

1. **L929 多检测：**分开验证每组 6 孔究竟是独立单位还是技术孔；区分 CCK-8 重复测量与活死染色终末取样；每项 Assay 有自己的时间锚点。
2. **GelMA 生物安全性：**复用浸提液步骤块，测试同一预期材料供多个 Assay 与分别制备两种情形；测试本次浓度绑定和命名参数预设；不把目标产物写成实际材料。
3. **SA 铜梯度：**重算母液加样与最终浓度，保留单位、基准和公式；处理“记录总体积与后续取样量不一致”的来源冲突，不自动选择解释。
4. **生物膜多 Assay：**验证 CV、CFU、染色/显微镜的样本分配、终末使用和载体差异；仅对确切已知的不兼容流程阻断。
5. **陌生实验：**允许添加自定义字段和文本步骤，准确标出哪些字段目前无法计算，不把“不认识”当成非法设计。

通过标准是：用户可以沿着引导形成清楚的可执行草案；Agent 不误选对象、不偷填关键值、不把计划改成事实；计算能复核；复杂关系默认不压到用户面前；真实记录发现模型表达不了时能有边界地扩展，而不推倒重来。
