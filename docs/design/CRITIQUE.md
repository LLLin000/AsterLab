# Web Run Design Critique

- 日期：2026-11-08
- 对象：现有 Web Run 执行页与结果页
- 方法：Impeccable **Operate** rubric + 源码/浏览器走查 + live detector
- 证据：[BASELINE.md](BASELINE.md)、`docs/design/baseline/*.png`、`target/impeccable-run.json`
- 限制：**不是用户测试，也不是完整双评估 critique**；结论用于迁移基线和设计决策。

## Verdict

**设计具体性：中上。**  
时间点、Assay、检查、孔位、记录这些对象是 AsterLab 特有的，不像通用 dashboard 可以原样换产品名。但 Run 页当前的页面组织仍像“多个等权卡片 + 一个大表单”，没有把“执行者在实验台前的动作顺序”变成布局。

**主要矛盾：** 当前任务、就绪条件、记录入口在视觉上分散；记录虽然已经回到 Run，但仍不是首屏的主工作面。

## Strengths

1. **未知状态没有伪装成确定值。**  
   “未绑定”“无已解析参数”“未开始”都明确出现，保留了科学边界。

2. **完成与测量已经开始分离。**  
   “确认只记录操作完成；读数单独保存”比把两者混成一个按钮更符合执行事实。

3. **时间点和任务条是产品特有的。**  
   D1/D3/D7 + 任务 chip 能快速建立执行顺序；这是比通用 tabs 更好的方向。

4. **视觉克制。**  
   暖灰/紫（在浅色 token 下）和细线结构有工具感，没有营销页的装饰。

## Priority issues

### P1 — 当前任务和记录不在同一个视觉工作面

**证据**：`runs-record-1440.png` 中，当前任务卡片、三个模块卡片、确认/记录卡片依次堆叠；结构化记录表在 1440×1000 首屏下方。

**影响**：执行者需要滚动才能看到“这一步要记什么”，而记录才是当前任务的核心动作。

**方向**：把当前任务 + 记录合成一个工作表；材料/仪器/检查收进右侧紧凑就绪栏。记录区上移，主操作跟随记录。

### P1 — 三个空模块获得与记录相同的视觉重量

**证据**：材料与试剂 / 仪器与程序 / 检查与接受三个并排卡片，全部“未绑定”，占满一行。

**影响**：空状态比真实任务更醒目；用户先看到“没有绑定”，而不是“现在要记录什么”。

**方向**：就绪栏用一行一个状态，显示“未绑定 · 绑定”即可；没有内容时不画三张空卡。

### P1 — 主操作位置过深

**证据**：`确认完成并进入下一步` 在记录表、检查、偏差之后；首屏不可见。

**影响**：完成本步的路径被记录字段拉长；用户不知道页面是否还有下一步。

**方向**：记录区底部固定操作条；测量保存与完成本步分开但相邻。阻断时操作条写明原因，而不是只禁用按钮。

### P1 — 实际主题与 DESIGN.md 不一致

**证据**：
- 默认 `<html data-bs-theme="dark">`，背景 `#101318`；
- light token 背景 `#f7f8fa`、accent `#2563eb`；
- DESIGN.md：背景 `#f7f6f3`、accent `#5b45c9`。

**影响**：Rune 迁移会继承错误 token，导致 Web/Rune 视觉分叉；也会让“暖灰 + 紫色”的决策失效。

**方向**：迁移前把 `tokens.css` 与 DESIGN.md 对齐；明确 dark 是另一套 token，不是默认冒充 light。Rune theme 从同一源生成。

### P2 — 10px 功能文字和低对比主按钮

**证据**：live detector 7 个 10px functional text；主按钮白字 `#6d8cff` = 3.1:1。

**影响**：高 DPI/小屏可读性差；主操作在深色背景上不够确定。

**方向**：功能文字最低 11px，推荐 12px；主按钮对比达到 4.5:1，或改用更深 accent/白字组合。Rune 迁移前把该规则写进组件契约。

### P2 — 当前任务状态与“选中任务”混淆

**证据**：点击已完成的 CCK-8 read 回看后，后续 Stain/Image 显示“未开始”；页面仍标“当前任务 3/5”。

**影响**：回看态与执行态混在一起；用户可能误以为后续步骤尚未执行，或当前任务被重置。

**方向**：区分 `selected task`（回看）与 `current task`（执行）；回看时标题改为“任务回看”，主按钮隐藏/禁用，进度仍按 Run 状态显示。

### P2 — 记录区文案重复

**证据**：`确认 / 记录`、`本步读数 · CCK-8 读板记录`、`本任务记录` 三层标题；说明文字重复“只记录操作完成”。

**影响**：视觉噪声；用户需要判断三个标题之间的关系。

**方向**：一个区块标题“本步记录”；测量表作为其子区；历史记录放在下方独立“本步事件”。

### P3 — 空状态与卡片层级

**证据**：页面多个大卡片、留白多；移动端关系图/模块会拉长首屏。

**方向**：用分隔线、行和单一工作面替代卡片堆叠；空状态用一句行动句，不占整卡。

## Cognitive load

- 可见选项：模式 tabs、时间点、任务 chips、模块、记录、检查、偏差、历史——一屏决策点超过 4 个。
- 当前任务不是最显眼的对象；“未绑定”和“确认/记录”竞争注意力。
- 执行者需要理解“完成”和“测量”两个事件，但页面没有用结构明确表达；文案是唯一提示。
- 回看态与执行态没有明确模式切换。

## What to keep

- 时间点/任务条的产品特有结构。
- 明确未知的文字状态。
- 完成与测量分离的语义。
- 暖灰 + 单紫色强调，不引入第二套装饰色。
- 记录在 Run 内，不做独立页面。

## What not to do

- 不要为了“原生感”增加玻璃、渐变、发光或装饰性动画。
- 不要用通用 dashboard 卡片替代任务/记录关系。
- 不要把测量表做成第二次要表单；它是当前任务的一部分。
- 不要让 Rune 组件默认视觉决定 AsterLab 的视觉。
- 不要在 token 未对齐前迁移 Rune。

## Next design decision

建议先做 **Run 工作表重排**：

```text
当前任务
├─ 左：本步记录（结构化字段 + 偏差 + 完成/保存）
└─ 右：就绪栏（材料/仪器/检查）
```

这比先做全应用视觉 polish 更能验证信息架构，也直接决定 Rune Run slice 的布局。
