# AsterLab v1.2 Desktop UI — blunt gap audit

- Baseline under review: native desktop UI at `O:/v12-ux-review` (the current Slint app and Rune captures), compared with the HTML workspace in `web/view.html` / `web/app.js` and `docs/design/2026-11-09-v1.2-native-product-spec.md`.
- Evidence: source inspection plus committed screenshots `rune-page-design.png`, `rune-page-protocol.png`, `rune-page-tools.png`, `rune-gate2-900.png`, `rune-gate2-dark.png`, and `rune-run-read.png`. The first five screenshots are 1200×760 or 900×600 captures; the Run read view is a 1840×1200 capture. These are screenshots, not a claim of a current real-window walkthrough. No 900×600 dark capture, keyboard end-to-end evidence, loading/error capture, or live accessibility-tree evidence was found for the full native app.
- Verdict: **Reject as a usable scientific workspace.** It is a useful read-only interaction spike, not a product-grade replacement for the HTML workspace. The most serious gaps are no durable authoring/execution, missing usable Tools, and no distinct Project workspace.

## Blocking issues (ordered)

1. **P0 — The main affordance is not a working scientific workflow.** `apps/desktop/src/main.rs` describes an explicitly read-only database viewer; it loads a read model and holds a `Draft` in app memory. The visible “保存读数” action in the Run capture has no corresponding save/write callback in `AppWindow.slint` (the app wires selection, mode, question, and group metric callbacks only). Design edits therefore cannot be represented as durable Core saves/reopen/CreateRun behavior. A polished-looking button cannot imply data was saved.
2. **P0 — Project is not a project workspace; Tools is not a tools workspace.** The project screenshot is effectively navigation context plus design summary, and the Tools screenshot is an empty “记录 / 暂无记录” view. There is no supported project create/import/backup/continue-work path or actionable plate/calculator/parameter-table/component-library/structured-import workflow. This falls short of the explicit product contract.
3. **P1 — Designer is an information dump, not a design canvas.** The capture presents summary text and a horizontal step strip, with no visible relationship map, no material/sample assignment map, no editable inspector, no save/review/create-run path. The captured 1200×760 design view leaves most of the lower window blank. HTML `view.html` has an actual pan/zoom/select/connect canvas and component detail surface; the native capture does not approach that information architecture.
4. **P1 — Protocol is only a list.** Screenshot shows protocol names and versions as plain rows with no selected detail, purpose, step navigation, parameters/units, materials/instruments, checks, outputs, source/version links, or actionable version/edit/bind controls. There is no obvious empty, loading, unresolved, or failure state.
5. **P1 — Run semantics and persistence are unsafe to infer from the UI.** The native capture presents a compact single-step record form and three “未绑定” items beside it; no clear raw-vs-derived distinction, lineage, batch/plate context, validation preview, save receipt, saved/unsaved state, or durable restart proof is visible. A separate Run read screenshot renders internal enum values (`in_progress`, `completed`, `not_started`) directly. The current product spec requires validated 50/50 layout, 96-well batch path, paste preview, distinct missing/invalid state, and save-state clarity.
6. **P1 — Shell consumes too much narrow-window width.** In the 900×600 screenshot, the 56px rail is followed by a fixed, roughly 260px navigation/context pane before the page content. This is the opposite of the v1.2 requirement to collapse context at 900×600; the usable work area is squeezed, and the composition remains a navigation tree rather than the specified primary rail + contextual content.

## Cross-cutting quality gaps

- **Information hierarchy / density:** Rail + wide context tree + sparse page content creates a demo shell, not task-oriented density. The design view spends its first screen on summaries and step pills rather than a navigable relationship model and selected-object inspector. Protocol and Tools are mostly blank. Run has actionable controls but lacks the surrounding context that makes recording scientifically trustworthy.
- **Empty/loading/error:** Captures show a few ad hoc empty labels (“暂无记录”, “本设计暂无运行记录”, “没有该检测的实际培养板记录”). There is no consistent empty-state action, loading indicator, recoverable database error state in-window, or unresolved/unsupported object presentation. Source does map some missing values to “未记录” / “待确认”; that is not a complete state system.
- **Keyboard/accessibility:** Product spec requires visible 2px focus ring and keyboard-visible interaction. Captures provide no evidence of a full keyboard path, focus order, shortcuts, or focus styling. Some clickable group/assay regions have accessible roles/actions in Slint source, but this does not demonstrate keyboard completeness for the workspace. **Do not mark PASS.**
- **900×600:** Screenshot evidence shows fixed-width context navigation and cramped content; spec explicitly says context collapses and content scrolls. Run has a 900×600 capture, but no evidence that each page has independently usable 900×600 behavior or that clipping/scroll ownership is correct.
- **Dark mode:** `rune-gate2-dark.png` demonstrates a dark rendering of Run only, with content still sparse and unbound modules still prominent. It does not verify all five pages, contrast ratios, focus, disabled/selected/error state distinction, or dark-mode semantic colors. **No dark-mode PASS.**
- **Localization/internal copy:** UI is mixed Chinese/English (`GeIMA/ZnO L929 biocompatibility`, `Seed L929`, `Apply extracts`, `CCK-8 read`, `LIVE/DEAD`, `Protocol`, `Run`); Run read view exposes machine states `in_progress`, `completed`, `not_started`. Technical labels can remain standard where useful, but workflow copy and status values need user-facing localization. `AboutWindow` calls the product an “界面验证原型”; that is honest metadata, not shippable product copy.
- **Hardcoded data:** Source selects the first project on launch; screenshot fixture is a fixed L929 dataset/run. This is not proof of hardcoding in the data layer, but it makes the captured experience appear like a single-project demo and gives no explicit recent/last-used selection. No default selection safety or unsaved-change context is shown.
- **Callbacks / affordances:** Inspected selection, mode, group, assay, well and question callbacks are wired; no basis to label those dead. Conversely, save/run-create/project-create/import/tool actions are absent from the callback contract. Where buttons imply persistence or execution, this is the more serious problem: a visible affordance without a real operation.

## Rejection decision

**Reject v1.2 desktop UI as product-ready; accept only as a read-only feasibility spike.** The screenshots establish a real native-rendered UI in selected states, but not a working product or a passing audit. Before reconsideration, require durable Core-backed behavior for design and Run, actual Project and Tools pages, Protocol detail, explicit save/error/empty states, and a real-window evidence set for all five pages at 900×600 and dark mode with keyboard interaction. No dimension is a PASS on the current evidence.
